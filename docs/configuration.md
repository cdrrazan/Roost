# Configuration reference

roost reads one YAML file. It is found in this order, first hit wins:

1. `--config /path/to/file`
2. `$ROOST_CONFIG`
3. `./roost.yml` (project-local escape hatch)
4. `~/.roost/config.yml` (the default, and the normal case)

All app paths are made absolute at load time: `~` expands to your home
directory and relative paths resolve against the config file's own directory.

## Top-level keys

```yaml
domain: demo.example.com   # OPTIONAL fallback for bare-path apps
include:                   # OPTIONAL glob(s) pulling apps from other files
  - apps/*.yml
tunnel:
  name: roost              # explicit; never generated by roost
  access:                  # optional; omit to leave apps public (roost warns)
    emails:
      - me@example.com
defaults:                  # optional per-app defaults
  memory: 512m
  profile: core
apps: [...]                # see below
```

## App entries — two forms, freely mixed

**Bare string** — a path; the hostname comes from the global `domain`:

```yaml
apps:
  - ~/projects/app1        # → app1.demo.example.com
```

**Map** — everything overridable:

```yaml
apps:
  - path: ~/work/legacy-crm   # required
    domain: crm.example.com   # verbatim FQDN; ignores the global domain
    name: crm                 # default: slugified folder basename
    framework: rails          # default: detected (see `roost detect`)
    port: 3001                # default: framework default
    database: mysql           # default: detected from the app's config
    memory: 768m              # default: defaults.memory, then 512m
    profile: extras           # start only with --profile extras
    env:                      # runtime environment (container)
      SOME_KEY: value
    build_env:                # build-time environment (Docker builder stage)
      SKIP_ENV_VALIDATION: "1"
```

`env` is set at container runtime; `build_env` is set during the image build
(rendered as `ENV` in the Dockerfile's builder stage). Use `build_env` for
frameworks that validate configuration during their build — e.g. a Next.js app
using `@t3-oss/env`, whose `next build` needs `SKIP_ENV_VALIDATION` since the
runtime env isn't present at build time. **`build_env` values bake into image
layers** (visible via `docker history`), so keep secrets in `env`; `build_env`
is for non-secret build flags.

## Splitting the app list across files — `include`

When one file grows unwieldy, move apps into separate files and pull them in
with `include`. It takes a single glob or a list of globs; each pattern
resolves against the main config file's directory.

```yaml
# ~/.roost/config.yml
domain: example.com
include: apps/*.yml       # or a list: [core/*.yml, side-projects/*.yml]
apps:
  - ~/projects/dashboard  # the main file may still list apps of its own
```

Each included file contains **only** an `apps:` list — nothing else. A
`domain:`, `tunnel:`, `defaults:`, or a nested `include:` in an included file
is an error; those stay in the main file. Group apps however you like: one
file per app, or one file per feature holding several.

```yaml
# ~/.roost/apps/blog.yml
apps:
  - path: ../projects/blog     # relative to THIS file's directory
    domain: blog.example.com
    framework: rails
```

Resolution details:

- **Paths in an included file resolve against that file's own directory**
  (`~` still expands to home; absolute paths are used as-is), so a file can
  sit next to the code it points at.
- Apps are assembled in order: the main file's own `apps:` first, then each
  `include` pattern in the order listed, each pattern's matches in sorted
  filename order.
- A pattern that matches **no files** is an error, not a silent skip — a typo
  in a glob never quietly drops apps.
- Two apps resolving to the same hostname is the same hard error whether they
  came from one file or several.

## Hostname resolution — one app, one hostname

1. If the app sets `domain:`, that value **is** the FQDN, used verbatim.
2. Otherwise, with a global `domain:` set, the FQDN is `<name>.<domain>`.
3. Otherwise the app is **skipped** — with a printed reason, never silently.
   The other apps still run. Same for a `path` that doesn't exist.

Hostnames are validated, never repaired: URLs, ports, paths, bare labels,
trailing dots, and over-length labels are each rejected with a message that
names the app (and, for URLs and ports, states the correct value). Two apps
resolving to the same FQDN is a hard error naming both apps.

## Database setup and seeding on `up` — `seed:`

Any database-backed app is **migrated on every `roost up`** — Rails via
`bin/rails db:prepare`, Django via `python manage.py migrate` — so a freshly
started stack always has an up-to-date schema without a manual `exec`.

An app can also be **seeded** by adding `seed:` to its entry:

```yaml
apps:
  - path: ~/code/blog
    seed: true                                    # framework default seed cmd
  - path: ~/code/shop
    seed: "bin/rails db:reset && bin/rails db:seed"  # explicit command
```

- `seed: true` runs the framework's default seed command (Rails: `bin/rails
  db:seed`). Frameworks without a conventional seed task (everything but Rails)
  must give an explicit command string, or `roost up` reports the error.
- `seed: "<command>"` runs that command in the app container via `sh -lc`, so
  it can chain steps or set inline env.
- Seeds run **once per app**: the first successful seed is recorded in
  `~/.roost/state.json`, and later ups skip it. `roost up --reseed` forces every
  seed-enabled app to seed again.
- The seed step always executes with `SEED_DEMO=1` in its environment, so demo
  seeds that gate on that variable run when roost seeds them.
- Absent or `seed: false` disables seeding; migration still runs for DB apps.

Pair this with [`seed.env`](#shared-demo-credentials--roostseedenv) below to seed
the same super-admin login across every app.

## Shared demo credentials — `~/.roost/seed.env`

An optional `~/.roost/seed.env` holds credentials shared across every app so a
single demo super-admin logs into all of them. It is a plain `KEY=VALUE` file —
blank lines and `#`-comments are ignored, and matching surrounding quotes are
stripped:

```bash
# ~/.roost/seed.env  (mode 0600)
SEED_ADMIN_EMAIL=me@example.com
SEED_ADMIN_PASSWORD=one-strong-shared-secret
```

roost injects every pair into the compose `environment:` of each **non-static**
app, positioned **below** that app's own `env:` so an explicit per-app value
still wins. Each app's seed script reads the variables with a standalone
fallback:

```ruby
admin_email    = ENV.fetch("SEED_ADMIN_EMAIL", "demo@example.com")
admin_password = ENV.fetch("SEED_ADMIN_PASSWORD", "password123")
```

Notes:

- The file is **opt-in**: if it is absent, nothing is injected.
- Like the API token, these secrets live outside `config.yml`. Keep the file at
  mode `0600`; it is never written into your app repos.
- The variable names are your convention — roost passes through whatever keys
  the file contains; it does not interpret them.

## Things that trip people up

- **Nested global domains** (`domain: demo.example.com`) put every app two
  levels below the zone apex, which free Universal SSL does **not** cover.
  `roost doctor` flags this with the three fixes; the cheapest is a flatter
  domain.
- **Renaming `tunnel.name`** after a tunnel exists does not rename the remote
  tunnel — it points roost at a different one. `doctor` explains this state;
  `tunnel setup --adopt` switches deliberately.
- The Cloudflare API token lives in `$CLOUDFLARE_API_TOKEN` or
  `~/.roost/credentials` (0600 enforced) — never in this file.
